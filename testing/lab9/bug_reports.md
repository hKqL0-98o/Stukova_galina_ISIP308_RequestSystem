## BUG-01. Ответ HTTP 500 на идентификатор больше 2⁶³−1

| Поле | Содержание |
|---|---|
| Среда и версия | локальный стенд `127.0.0.1:5077`, версия 2.0.0, код до исправления |
| Шаги воспроизведения | 1. Запустить приложение. 2. Выполнить `GET /api/requests/10000000000000000000000000` под admin. Аналогично: `?status_id=<то же число>`, `POST /api/requests` с `category_id` или `applicant_id` = 10²⁵ или строкой из 5000 цифр, `PATCH /api/requests/1` с `status_id`/`executor_id`/`category_id` = 10²⁵, `DELETE /api/requests/<10²⁵>`, веб-страница `/requests/<10²⁵>`. |
| Ожидаемый результат | HTTP 404 (заявки с таким номером нет) для адреса; HTTP 422 для значения в теле запроса или фильтре |
| Фактический результат | HTTP 500 `{"error":{"code":"internal_error",…}}`; в журнале сервера `OverflowError: Python int too large to convert to SQLite INTEGER` |
| Важность | **Medium**: ошибка сервера минимум в 13 точках API и веб-интерфейса на простом вводе; данные не повреждаются, сервер продолжает работать |
| Доказательство | `evidence/before/TC-17.txt`; `test_run_before_fix.txt` (12 падений `test_bug01_…`, плюс `test_strange_identifiers_give_404`, `test_web_page_for_huge_identifier_is_404`) |
| Причина | Идентификатор передавался в SQL без проверки диапазона, а SQLite хранит INTEGER в 64 битах |
| Исправление | `src/services.py`: константа `SQLITE_INT_MAX`; `_parse_id` отклоняет значения вне диапазона и строки длиннее 19 цифр; новая `_find_request` считает такие номера несуществующими заявками (404) |
| Статус | **Повторно проверен**: TC-17 PASS, `test_regression.py::test_bug01_*` PASS |

## BUG-02. Ответ HTTP 500 при поиске по длинному числу

| Поле | Содержание |
|---|---|
| Среда и версия | то же |
| Шаги воспроизведения | `GET /api/requests?search=99999999999999999999` (20 цифр) под admin; также 19 цифр, `#` + 30 цифр |
| Ожидаемый результат | HTTP 200 и пустой список (такой заявки нет) |
| Фактический результат | HTTP 500 `internal_error`, в журнале `OverflowError` |
| Важность | **Low**: поле поиска доступно любому пользователю, но данные не затронуты |
| Доказательство | `evidence/before/TC-18.txt`; `test_run_before_fix.txt` (4 падения `test_bug02_…`) |
| Причина | Поиск по тексту «12345…» также ищет заявку с таким номером (`r.id = ?`); длинное число не помещается в INTEGER |
| Исправление | `src/repositories.py`, `find_requests`: поиск по номеру только если в числе не больше 18 цифр |
| Статус | **Повторно проверен**: TC-18 PASS, `test_bug02_*` PASS; поиск по обычному номеру (`#7`) работает (REG-03) |

## BUG-03. Управляющие символы в тексте: 500 в теме, мусор в описании и комментариях

| Поле | Содержание |
|---|---|
| Среда и версия | то же |
| Шаги воспроизведения | 1. `POST /api/requests` под operator с `"title": "до\u0000после"`. 2. То же с символом NUL в `description`. 3. `POST /api/requests/1/comments` с `"content": "a\u0000b"`. 4. Тема с символом `\u0007` (звонок). |
| Ожидаемый результат | HTTP 422 `validation_error`: ввод с управляющими символами отклоняется |
| Фактический результат | 1) HTTP 500 `database_error` (сработал `CHECK` в БД; по-видимому, SQLite считает длину строки до NUL). 2–4) HTTP 201: символы сохранены в БД как есть |
| Важность | **Low**: нужен специально сформированный ввод; в БД попадает «мусор», который может ломать экспорт и отображение |
| Доказательство | `evidence/before/TC-11.txt`; `test_run_before_fix.txt` (6 падений `test_bug03_…`) |
| Исправление | `src/services.py`: `CONTROL_CHARS` и проверка в `_parse_text`; допустимы табуляция и переводы строк |
| Статус | **Повторно проверен**: TC-11 PASS, `test_bug03_*` PASS, многострочный текст по-прежнему принимается (REG-07) |

## BUG-04. Форма смены статуса по умолчанию предлагает «Новая» и позволяет случайно вернуть заявку в начальный статус

| Поле | Содержание |
|---|---|
| Среда и версия | Windows, Chrome (последняя версия), `python app.py`, версия 2.0.0, коммит `6661553` (develop), временная БД из `seed.sql` |
| Шаги воспроизведения | 1. Войти как `operator`, открыть заявку №2 (статус «В работе»). 2. Посмотреть выпадающий список «Сменить статус» в блоке «Управление заявкой». То же для исполнителя `petrov` у заявки, переведённой в «В работе». |

| Доказательство | `evidence/BUG-04_before.png` |
| Исправление | `templates/request_detail.html`: в начало списка добавлен пункт «Выберите новый статус» (`selected disabled`), у списка стоит `required` |
| Статус | **Новый** |

## Проверено и дефектом не является

Эти случаи сначала выглядели подозрительными. Проверка показала, что приложение работает правильно.

1. **Пустой приоритет** (`"priority": ""` при создании) принимается и заменяется на «Средний». Это задуманное поведение, значение по умолчанию. Первая версия автотеста ошибочно ожидала 422, тест исправлен, код нет.
2. **Параметр `next` при входе** (`/\evil.example`, `//evil.example`, `https://evil.example`): переход на внешний сайт невозможен. Адрес либо отбрасывается, либо `\` кодируется как `%5C`. Первая версия проверки в тесте была написана неверно, исправлена.

## Замечания (не дефекты, в работе не менялись)

- Формы веб-интерфейса не содержат CSRF-токена. Частично сдерживает `SameSite=Lax` на cookie сессии. Для учебного проекта оставлено как известное ограничение.
- `PUT /api/requests/{id}` работает как `PATCH` (частичное обновление), это описано в README.
- Сайт при деплое работает по HTTP без шифрования (описано в README).
