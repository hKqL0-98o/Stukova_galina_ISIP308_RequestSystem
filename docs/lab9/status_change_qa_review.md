# ЛР №9. Ревью набора кейсов «Смена статуса заявки» и результаты запуска

Ревью выполнено нейросетью по запросу студентки (AI-журнал, ЛР №9, запись 2). Объект: `docs/lab9/status_change_qa_cases.md` (31 кейс). Затем 28 кейсов запущены на реальном приложении (`testing/lab9/run_status_cases.py`): SC-07 (веб-форма), SC-10 (перезапуск) и SC-30 (одновременная правка) выполняются только вручную.

## 1. Замечания к набору (по критичности)

### Critical

**R1. Ожидаемые результаты частично подогнаны под реализацию, а не взяты из ТЗ.**
Тексты ошибок в SC-12…SC-18 и SC-20…SC-23 автор набора прочитал в `src/services.py` до написания кейсов. Поэтому эти кейсы не могут поймать неверный текст или код ответа: проверка круговая. В ТЗ текстов ошибок нет, источник ожидания нужно указывать в каждой строке («ТЗ ФТ-6» или «поведение, принятое в проекте»), а тексты вынести в контракт API, а не в тест.

**R2. Набор не отражает противоречие между ТЗ и проектом: кто вправе менять статус.**
По ТЗ статусы меняет **исполнитель**; оператор «регистрирует заявки и назначает исполнителей», администратор управляет учётными записями и категориями. В наборе статусы меняют оператор (SC-06, 20, 21, 22) и администратор (SC-05, 29): основание только README, а не ТЗ. Нужен отдельный кейс «оператор меняет статус» с ожиданием по ТЗ (403) либо правка ТЗ.

### High

**R3. SC-26 и SC-27: ожидаемый результат придуман.** ТЗ говорит только «последовательно». Текст сообщения и код 422 взяты по самому строгому прочтению, приоритет High при неопределённом требовании. Кейсы нужно пометить «ожидание не из ТЗ, решение за заказчиком».

**R4. Нет матрицы «роль × текущий статус × целевой статус».** Это 4 × 4 × 3 = 48 комбинаций, набор покрывает их выборочно. Не покрыты, например: исполнитель на закрытой заявке, заявитель «Новая → Закрыта», исполнитель «Новая → Закрыта». Лучше решать параметризованным pytest (ЛР №10).

**R5. Веб-интерфейс почти не покрыт** (только SC-07). Нет: прямой POST формы с запрещённым статусом в обход скрытых вариантов, отображения ошибки 422 в форме, заявителя (в списке только «Закрыта» для выполненной заявки), перехода на `/login` без входа.

**R6. Нет кейсов на деактивированных и неподходящих пользователей:** вход деактивированного пользователя, назначение исполнителем деактивированного пользователя или заявителя (в `services.py` есть проверка активности и роли).

### Medium

**R7. Расплывчатые ожидаемые результаты:** SC-30 («хорошая практика»), SC-31 (не указаны машина и способ: максимум или медиана), SC-27 («требует уточнения»), SC-08 («поля кто, когда…» без точного списка), SC-10 («история на месте» без перечня записей).

**R8. Граничные значения `status_id` исчерпаны не до конца.** Есть SC-24 (`"abc"`, `-1`, `0`, `true`, `3.5`). Нет: пустого тела, `null`, строки `"3"`, числа 10^25, пробелов.

**R9. Дубли:** SC-04 повторяет цепочку SC-01…SC-03; SC-19 и SC-22 проверяют одно (отказ откатывает весь запрос); SC-12 и SC-13 — одно правило для двух ролей (оправдано матрицей). Четыре кейса дублируют прежние TC-06, TC-09, TC-21, TC-25 из набора ЛР №9.

**R10. История изменений проверена только на добавление.** Нет: неизменяемости записей через API, порядка и меток времени, поведения при удалении заявки.

### Low

**R11. Приоритеты:** SC-26 назначен High при открытом требовании; SC-10 (требование НФТ-2) стоит выше Medium относительно SC-09.

**R12. Нет кейса на `PUT`** (по README он равен `PATCH`) и на неверный пароль при смене статуса (401 и счётчик попыток).

### Разбор двух FAIL

**SC-26 (пропуск «В работе»): FAIL.** Исполнитель перевёл заявку «Новая» сразу в «Выполнена», ответ 200. ТЗ (критерий приёмки 3) требует менять статус «последовательно». Проект же разрешает любой переход, кроме закрытия, и это записано в README («Меняет статус: кроме «Закрыта»»). Расхождение между ТЗ и реализацией; ошибкой оно считается, только если «последовательно» понимать строго. То же ограничение найдено ревью API-контракта (ЛР №7) и было записано в ограничения; теперь оно подтверждено воспроизводимым кейсом и оформлено как **BUG-05** (`testing/lab9/bug_reports.md`).

**SC-27 (откат «Выполнена» → «В работе»): FAIL.** Ответ 200, статус изменился. ТЗ откат не описывает, поэтому ожидание кейса не из ТЗ (замечание R3). Решение зависит от заказчика.

## 3. Исправление BUG-05 (ветка `fix/status-sequence`) и повторный прогон

Решение: оператор и исполнитель переводят заявку только на один шаг вперёд (Новая → В работе → Выполнена → Закрыта), закрывает заявитель по прежним правилам, администратор может любой переход. Нарушение порядка: 422, `details.status_id = invalid_transition`. Интерфейс предлагает только допустимый следующий статус.

| Проверка | До исправления | После исправления |
|---|---|---|
| SC-26 (пропуск «В работе») | FAIL, HTTP 200 | **PASS**, HTTP 422, «Статусы меняются последовательно: из «Новая» можно перейти только в «В работе»» |
| SC-27 (откат «Выполнена» → «В работе») | FAIL, HTTP 200 | **PASS**, HTTP 422, статус остался «Выполнена» |
| Набор SC (28 запущенных кейсов) | 26 PASS, 2 FAIL | **28 PASS** (`testing/lab9/results_status_cases.json`; до исправления: `results_status_cases_before.json`) |
| Новые автотесты ST-01…ST-09 (12 тестов) | 6 FAIL, 6 PASS (`testing/lab10/test_run_bug05_before_fix.txt`) | **12 PASS** |
| Прежний набор ЛР №9 (31 кейс) | 31 PASS | 31 PASS |
| Весь набор pytest | 130 passed | **142 passed** |

Что изменилось в поведении и осталось неизменным: администратор по-прежнему может переоткрыть закрытую заявку (SC-29) и сделать любой переход; установка текущего статуса остаётся допустимой (SC-28); запрет закрытия для оператора и исполнителя (ФТ-6) проверяется до проверки порядка, поэтому ответ 403 в этих случаях не изменился. Исследовательская проверка X-02 (оператор меняет статус) остаётся открытым расхождением ТЗ и README: исправление её не затрагивает.

**Ограничение:** возврат на предыдущий статус для не-администратора теперь невозможен (например, заявитель не может вернуть выполненную заявку в работу). ТЗ это не описывает, при необходимости такое действие выполняет администратор.
