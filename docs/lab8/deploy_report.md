# ЛР №8. Развёртывание на удалённом сервере (17.11.2026)

## Среда

| Параметр | Значение |
|---|---|
| Сервис | Яндекс Облако, Compute Cloud, ВМ `helpdesk` (зона `ru-central1-a`) |
| Ресурсы | 2 vCPU с гарантированной долей 20% (Intel Ice Lake), 2 ГиБ RAM, HDD 18 ГиБ, публичный IPv4 |
| ОС | Ubuntu 24.04.5 LTS (ядро 6.8) |
| Docker | Docker 29.10.0, Docker Compose v5.7.2 (установлены скриптом `get.docker.com`) |
| Доступ | вход по SSH-ключу (ed25519), пароль не используется |
| Адрес | `http://84.252.128.132/` (HTTP, без шифрования) |
| Версия кода | ветка `main`, коммит `8ec7e1f` (клонирован с GitHub) |

## Порядок действий (по README, раздел «Деплой на сервер»)

1. Создана ВМ, получен публичный адрес; подключение `ssh student@<адрес>` по ключу.
2. Установлен Docker, проверены `docker --version` и `docker compose version`.
3. `git clone` репозитория, `.env` создан из `.env.example`, в `SECRET_KEY` записано случайное значение (`openssl rand -hex 32`, 64 символа). Значение в отчёт не включено.
4. `docker compose up -d --build`: образ собран, контейнер `helpdesk` запущен.

## Что проверено на сервере

| Проверка | Результат |
|---|---|
| Статус контейнера | `Up`, `healthy` (HEALTHCHECK проходит) |
| Команда запуска | `waitress-serve --host=0.0.0.0 --port=5000 --threads=8 --call app:create_app` |
| Пользователь процесса | `uid=1000(appuser)`, не root |
| Права на данные | `/data` и `/data/requests.db` принадлежат uid 1000 |
| Том данных | именованный том `app_helpdesk-data`, смонтирован в `/data` |
| Предупреждение о `SECRET_KEY` в журнале | отсутствует (ключ свой) |
| `GET /health` снаружи | 200, `{"status":"ok","database":"ok","service":"HelpDesk RequestSystem","version":"2.0.0"}` |
| `GET /api/requests` без входа | 401 |
| `GET /docs` | 200, Swagger со всеми эндпоинтами |
| Вход в веб-интерфейс (оператор) | выполнен, виден список из 10 заявок |
| Форма смены статуса у заявки №7 («В работе») | в списке только «Выполнена» (порядок статусов, BUG-05) |
| Сохранность данных при пересоздании контейнера | `docker compose down` и `up -d` без `-v`: контейнер снова `healthy`, в журнале нового контейнера нет строки «База данных создана заново», то есть база `requests.db` осталась на томе |

Скриншоты: `docs/screenshots/deploy/` (`deploy_01_health.png`, `deploy_02_swagger.png`, `deploy_03_list.png`, `deploy_04_status_form.png`).

## Ограничения и что не проверялось

- Сайт работает по HTTP без шифрования, использовать только тестовые учётные записи. Сертификат и домен не настраивались.
- Сохранность проверена по журналу запуска и неизменному файлу базы; новые заявки перед пересозданием не создавались.
- Нагрузочное и кросс-браузерное тестирование на сервере не проводилось.
- Виртуальная машина создана на время проверки работы и будет удалена после сдачи; адрес после этого перестанет отвечать.
- Права на `/data` при монтировании папки хоста (а не именованного тома) не проверялись.
