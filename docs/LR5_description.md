## Что было не так в первой версии и что исправлено

| № | Проблема первой версии | Почему это ошибка | Исправление |

| 2 | В `Users` не было логина и пароля | ФТ-1 (вход по логину и паролю) и НФТ-4 (хеширование паролей) нельзя реализовать | Добавлены `login` (уникальный), `password_hash`, `is_active` |
| 3 | Не было таблицы истории | ФТ-9 требует хранить историю изменения статусов | Добавлена таблица `RequestHistory` |
| 4 | Не было приоритета | Приоритет есть во всех экранах прототипа (ЛР4) | Добавлен `Requests.priority` со списком допустимых значений |
| 5 | Категории не совпадали с ТЗ | В ТЗ одни 4 категории, в `seed.sql` другие | Категории приведены к ТЗ, добавлено поле `description`, оно было в ТЗ |
| 6 | Заявку с комментариями нельзя было удалить | Комментарии ссылались на заявку без правила удаления | `ON DELETE CASCADE` у `Comments` и `RequestHistory` |
| 7 | Не было ограничений на значения | Можно было записать роль «Директор», пустую тему, приоритет «Срочно» | Добавлены `CHECK` на роль, длину темы, описания и комментария, приоритет |
| 8 | Не было ER-диаграммы | Обязательный артефакт ЛР5 | `er_diagram.png` / `er_diagram.svg` / `er_diagram.mmd` |
| 9 | Не было файла запросов | Требуется 5 INSERT, 5 SELECT, 2 UPDATE, 2 DELETE, 3 WHERE, 2 JOIN | `queries.sql` + `queries_results.md` |
| 10 | В `seed.sql` все заявки были от одного заявителя | Нельзя проверить, что заявитель видит только свои заявки | Заявки распределены между двумя заявителями и двумя исполнителями |

## Таблицы

| Таблица | Назначение | Первичный ключ | Обязательные поля | Внешние ключи |
|---|---|---|---|---|
| Users | пользователи всех ролей | id | fio, login, password_hash, role | — |
| Statuses | справочник статусов | id | name | — |
| Categories | справочник категорий | id | name | — |
| Requests | заявки | id | title, priority, category_id, status_id, applicant_id | category_id → Categories, status_id → Statuses, applicant_id → Users, executor_id → Users |
| Comments | комментарии к заявкам | id | request_id, author_id, content | request_id → Requests (каскад), author_id → Users |
| RequestHistory | журнал изменений заявки | id | request_id, user_id, action | request_id → Requests (каскад), user_id → Users |

## Связи

Все связи «один ко многим» (1:M):

- **Статус → Заявки.** В одном статусе много заявок, у заявки ровно один статус.
- **Категория → Заявки.** Аналогично.
- **Пользователь → Заявки (как заявитель).** Обязательная связь.
- **Пользователь → Заявки (как исполнитель).** Необязательная: у новой заявки исполнителя может не быть.
- **Заявка → Комментарии, Пользователь → Комментарии.** Таблица `Comments` по сути реализует связь «многие ко многим» (M:M) между пользователями и заявками: один пользователь комментирует много заявок, у заявки комментарии от многих пользователей. При этом у каждой записи есть свои данные (текст, дата).
- **Заявка → История, Пользователь → История.** Так же, как у комментариев.

## Нормализация

- **1НФ.** Каждое поле хранит одно значение, повторяющихся групп нет: комментарии и история вынесены в отдельные таблицы, а не хранятся списком внутри заявки.
- **2НФ.** Все ключи простые (`id`), поэтому частичных зависимостей нет.
- **3НФ.** Названия статусов, категорий и ФИО не дублируются в заявках: заявка хранит только ссылки (`status_id`, `category_id`, `applicant_id`, `executor_id`). Переименование категории меняет одну строку.

Два осознанных отступления:

1. **Роль и приоритет хранятся текстом с `CHECK`, а не отдельными таблицами.** Списки маленькие и фиксированные (4 роли, 3 приоритета), у значений нет собственных атрибутов, а `CHECK` гарантирует, что посторонних значений не будет.
2. **В `RequestHistory` старое и новое значение записываются текстом** (например «Новая → В работе»). Это журнал: он должен показывать, как было в момент изменения, даже если статус или пользователя потом переименуют. Ссылка вместо текста «переписала» бы историю.

## Проверки из самопроверки методички

- **Внешние ключи настроены.** Проверено: заявка с несуществующей категорией и с несуществующим заявителем отклоняется, а удалить используемую категорию или пользователя нельзя (`queries_results.md`, раздел «Самопроверка»).
- **Скрипты можно выполнить повторно.** `schema.sql` начинается с `DROP TABLE IF EXISTS`, повторный запуск `schema.sql` + `seed.sql` возвращает базу к исходному состоянию (проверено).
- **Тестовые данные позволяют проверить функции.** Все 4 статуса и 4 категории, 3 приоритета; заявки с исполнителем и без; два заявителя и два исполнителя для проверки прав; есть комментарии и история.
- **Результаты запросов зафиксированы.** Текстом в `queries_results.md`; скриншоты нужно сделать самостоятельно (см. ниже).

## Как получить скриншоты для отчёта

1. Открыть `requests.db` в DB Browser for SQLite (или в VS Code с расширением SQLite).
2. Вкладка «Выполнить SQL» → вставить `queries.sql` целиком → выполнить.
3. Скриншоты: результат S1 (JOIN), S2 (WHERE + JOIN), сообщение «затронуто строк» после U1 и D2, результат S10.
4. После скриншотов вернуть базу к исходному состоянию: выполнить `schema.sql`, затем `seed.sql`.
