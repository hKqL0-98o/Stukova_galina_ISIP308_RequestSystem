## ЛР №8, запись 1. Генерация Dockerfile

**Дата и задача.** 17.11.2026. Получить Dockerfile для веб-приложения HelpDesk (Flask + SQLite) и инструкцию по монтированию тома для базы.

**Модель.** Claude Sonnet 5.5 (Anthropic) в Chatbox.

**Почему выбран этот вариант.** Модель работает в чате с прямым доступом к контексту и файлам репозитория (видит config.py, app.py, requirements.txt), что позволяет проверять запуск эндпоинтов без локальной установки Docker.

**Полный промпт.**

> Создай оптимизированный и безопасный Dockerfile для веб-приложения HelpDesk.
>
> Параметры проекта:
> Базовый образ: легкий образ на базе Python 3.12 (желательно python:3.12-slim).
> Стек: Flask, база данных SQLite.
> Точка входа для запуска: python app.py.
> Код и зависимости (requirements.txt) лежат в корне репозитория.
> Требования к Dockerfile:
> Настройка рабочей директории (например, /app).
> Кэширование слоёв (сначала копирование и установка зависимостей, затем копирование исходников).
> Открытие нужного порта для Flask (по умолчанию EXPOSE 5000).
> Корректная обработка буферизации вывода (ENV PYTHONUNBUFFERED=1).
> Пропиши инструкцию, как правильно смонтировать volume для SQLite, чтобы база данных не стиралась при перезапуске контейнера.

Формулировка промпта подготовлена в Gemini (Gemini 3.8 Flash), студентка проверила и отправила.

**Краткий результат.** Dockerfile на `python:3.12-slim`: `WORKDIR /app`, сначала `COPY requirements.txt` и `pip install`, потом код; `PYTHONUNBUFFERED=1`; `EXPOSE 5000`; пользователь `appuser` (uid 1000) и каталог `/data` с правами для него; `VOLUME ["/data"]`; `HEALTHCHECK` через `urllib` и `/health`; `CMD ["python", "app.py"]`. Отдельно модель указала, что без `HOST=0.0.0.0` приложение в контейнере недоступно снаружи (в `config.py` по умолчанию `127.0.0.1`), добавила `DATABASE_PATH=/data/requests.db`, две команды запуска с томом (именованный том и папка хоста с `chown`) и две оговорки: встроенный сервер Flask слабоват для публичного адреса, а без своего `SECRET_KEY` приложение стартует с известным ключом.

**Принято / изменено / отклонено.**
- Принято: порядок слоёв для кеша, `PYTHONUNBUFFERED`, `HOST=0.0.0.0`, `DATABASE_PATH=/data/requests.db`, запуск не от root, `HEALTHCHECK` без `curl`.
- Не принято для репозитория: `CMD python app.py` (в репозитории запуск через `waitress`), `VOLUME` в Dockerfile и `COPY --chown` на весь код (после ревью в записи 2 признаны недостатками).

**Самостоятельная проверка.** Модель запустила `python app.py` с `HOST=0.0.0.0`, `PORT` и `DATABASE_PATH` во временной папке: база создалась по заданному пути, `/health` ответил `{"status":"ok","database":"ok"}`. Сборка (`docker build`) и запуск контейнера **не выполнялись**: Docker на компьютере студентки не установлен. Студентка подтверждает: контейнер не собирался из-за отсутствия Docker на рабочей машине, логика проверялась прямым запуском кода приложения. **Дополнение 17.11 (вечером):** образ собран и запущен на виртуальной машине в Яндекс Облаке, контейнер `healthy`, база сохраняется в томе (`docs/lab8/deploy_report.md`); к моменту записи Dockerfile из ответа модели в таком виде не использовался: в репозитории запуск через waitress.

**Вклад студентки.** Сформулировала требования к Dockerfile; разобралась, зачем `python:3.12-slim` (меньше размер образа и поверхность атаки), зачем непривилегированный `appuser` и права `chown` на `/data`, почему зависимости копируются и ставятся до кода (слой с зависимостями берётся из кеша при правке `.py`), как `HEALTHCHECK` проверяет `/health` стандартной библиотекой без `curl`; зачем для SQLite нужен внешний том (без него база теряется при удалении или пересоздании контейнера, при обычном перезапуске она остаётся).
