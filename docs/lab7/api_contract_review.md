Модель: Claude Sonnet 5.5 (Anthropic), приложение Chatbox, 16.11.2026. Полные тексты промптов и ответов приведены в AI-журнале (раздел ЛР №7).

Ход работы:
1. Модели дали ТЗ и попросили предложить REST API-контракт для сущности «Заявка» (по ТЗ, не по готовому коду).
2. Отдельным промптом попросили критически проверить этот контракт.
3. Замечания сверены с реальным API скриптом на временной базе: `python verify_contract.py` (результаты в таблице). Рабочая база не затрагивалась.

## Реализованное замечание №1: до и после

До: серия из 30 запросов с неверным паролем давала 401 на каждый запрос, число попыток не ограничивалось.
После: 5 неверных паролей → 401, шестой запрос → 429 `too_many_requests` с заголовком `Retry-After`, верный пароль во время блокировки тоже не пускает. Успешный вход обнуляет счётчик. Блокировка действует на пару «адрес + логин», поэтому подбор с чужого адреса не закрывает вход настоящему пользователю.
Тесты `testing/lab10/test_login_rate_limit.py`: на коде без ограничения 4 из 8 падают (`test_run_rate_limit_before_fix.txt`), после изменений весь набор проходит (121 passed, `test_run.txt`).

## Отклонённое замечание №2: обоснование

Менять 403 на 404 для чужих заявок не стали:
- сервис внутренний, номера заявок последовательные, факт «заявка с номером N существует» практически ничего не раскрывает: содержимое остаётся закрытым;
- сообщение «Нет доступа к заявке» понятнее пользователю, чем «не найдена» (критерий удобства из ТЗ, НФТ-1);
- изменение сломало бы ранее проверенное поведение (кейс TC-20, регрессионные тесты и скриншот 403 в отчёте) и потребовало бы повторной проверки всего набора ради небольшого выигрыша;
- риск записан как известное ограничение в README и отчёте.

## Остающиеся ограничения (внесены в отчёт, раздел 7)

- нет защиты от одновременной смены статуса (проверка версии);
- допустимые переходы статусов шире, чем «последовательно» в ТЗ: оператор может пропустить шаг и откатить статус назад;
- список заявок без пагинации;
- счётчик попыток входа хранится в памяти процесса и сбрасывается при перезапуске; за обратным прокси нужен `X-Forwarded-For`.
